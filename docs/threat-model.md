# Threat model

English | [简体中文](threat-model.zh-CN.md)

Live Assistant turns browser actions into local shell and CLI input, so **being able to sign in to the page is equivalent to having the running user's shell privileges**. This document lists the trust boundaries, controls and known residual risks of the current implementation. For the architecture, see [Architecture](architecture.md).

## Trust boundaries

| Boundary | Trusted party | Untrusted content |
|---|---|---|
| Browser ↔ backend | The user who entered the correct password | Requests from other local/network sources, cross-site pages |
| Backend ↔ tmux/CLI | The user's direct keyboard actions, proposals approved by the user | Terminal output, "done" printed by a CLI, prompt text on the screen |
| Backend ↔ model | The user's words (via Live transcription) | Model output, the assistant's own words, quoted content, parts of the terminal content repeated by the model |
| CLI ↔ hook | Decisions returned by the backend via `hook.sock` | Tool arguments in the hook input (used only for display) |
| Backend ↔ Foundry | The local Entra login | Unvalidated endpoints, redirects |

## Threats and controls

| Threat | Controls | Residual risk |
|---|---|---|
| Remote or cross-site access to the shell | Listens only on `127.0.0.1`; exact Host check; Origin check on the login POST; the cookie is a random 256-bit value kept in memory, `HttpOnly` + `SameSite=Strict` (plus `Secure` over HTTPS), expiring after 8 hours; login is rate-limited; CSP `default-src 'self'`, static assets served locally | Other local users or processes that can reach loopback and know the password can sign in; when exposed through an SSH tunnel/reverse proxy, security depends on the tunnel and proxy configuration |
| Password leak | The password exists only in the backend process environment, is at least 16 characters, and is compared in constant time; it is not passed to session environments and is not written to `.env`, logs or state files | The process environment is visible to other processes of the same user |
| Model or terminal content impersonating authorization | Only the buttons or "批准/拒绝/始终允许 N" (approve/reject/always allow N) in the user's speech can decide a proposal; the assistant's words, quotes, terminal text and silence do not authorize; the interpreter only produces proposals and never executes anything; terminal content is marked as untrusted data in model prompts | Speech transcription errors may turn the user's words into a decision; both cards and voice reminders give the number and the exact content, which the user needs to check |
| Stale proposals or target drift | Proposals are bound to a session and an authorization epoch; the user taking over the keyboard, "等待反馈" (wait for feedback), or the process ending invalidates them; screen confirmations are invalidated when the prompt leaves the screen; if the user operated the terminal during interpretation, the card is annotated | Program output does not invalidate proposals (a human-in-the-loop trade-off), so the screen content may have changed by the time of approval |
| Abuse of always allow | Matches only an exactly identical `(kind, key)` in the same session (for key proposals the key is the whole normalized key sequence); cleared by revoke, "等待反馈" (wait for feedback), or the process ending; does not carry across sessions | No count or time limit: once approved, the same operation keeps being allowed automatically until the user revokes it |
| Screen recognition errors | Recognition of `[y/N]`, menus and trust dialogs only produces `prompt` proposals, and the card asks the user to check the terminal; ambiguous selection keys are not guessed | Pure terminal interaction has no cross-process atomicity; this is not a strong approval protocol |
| Hook channel misuse or failure | `hook.sock` has mode 600 and lives in the state directory with mode 700; the hook only accepts allow/deny; when the socket is unavailable, the backend has exited, or "Handle in terminal" (`在终端处理`) is chosen, the hook exits silently and the native prompt takes over | Other processes of the same user can connect to the socket; Codex requires the user to trust the hook inside the CLI with `/hooks` |
| CLI privilege overreach | CLI native permissions and sandboxes are not bypassed: each CLI is launched with the user's own configuration and no arguments (only hook arguments are appended), so permissions and sandboxing are determined by that configuration; the starting directory must be inside the workspace or `LIVE_ASSISTANT_ROOTS` (checked twice, by path and by real path, rejecting `..` and symlink escapes) | The CLI runs as the running user and reuses all of that user's local configuration and logins; the directory restriction only constrains the starting directory, and the process itself (especially a shell) is not confined to any directory |
| Credential leak | Foundry uses only Entra (`AzureCliCredential`) and no API key; tokens are kept only in memory and never written to configuration, arguments, terminals or web responses; the assistant does not proxy model requests for harnesses; when `LIVE_ASSISTANT_DSH_FOUNDRY_TOKEN` is enabled, DSH's `FOUNDRY_TOKEN` exists only in that session's process environment (not in argv, the tmux global environment, state files or web responses) and expires in about 1 hour; endpoints must be Foundry HTTPS root addresses, and requests do not follow redirects | The local `az login` state is itself a high-value credential; sessions inherit the backend environment (only `LIVE_ASSISTANT_PASSWORD` is removed), so other secrets in the backend environment are visible to harnesses and their child processes |
| Sensitive content sent to models | Terminal content sent to Live and the interpreter goes through `redact` (private keys, Bearer, common tokens, `password=` and the like, UUIDs, email addresses) and compression | Redaction is based on pattern matching and cannot recognize every secret; the user's terminal keeps the raw content |
| Conversation content written to disk | User and assistant transcripts are written to `live-transcript.jsonl` in the state directory (file 600, directory 700), each segment passed through `redact`, rotated above 4 MiB with only one old file kept; `events.jsonl` records only lengths, IDs and reasons, not what was said | Transcripts are redacted segment by segment, so secrets spanning segments may slip through; processes of the same user that can read the state directory can read recent conversations |
| Duplicate billing or lost sessions | The Live creation POST is not retried; an uncertain result is recorded as `uncertain` and blocks automatic re-creation; sessions with a known session ID are closed after a restart by reattaching to them | **There is no cost cap**; the harnesses' own model usage does not go through the assistant and is not recorded: billing continues as long as the voice connection stays open, and the UI shows only known usage, which is not the bill |
| State corruption or concurrent writes | Atomic writes (fsync + rename); after a write failure, further changes and terminal input are blocked; at startup the state directory is locked with an abstract socket, and a second backend is rejected before it changes any state | Other processes on the same machine can bind a socket with the same name first and prevent the backend from starting (affects availability only) |
| Input replay | A backend restart never re-sends any input; proposals that were approved but not confirmed as delivered are marked uncertain; verifications are not replayed | The user must judge for themselves whether an uncertain operation took effect |
| File upload overwrite or escape | An upload can only write a single file name (rejecting `/`, `\`, `..`), writes to a temporary file first and then publishes it with `link()`, so an existing file with the same name is never overwritten; upload and download paths are checked by real path and must be inside the workspace or `LIVE_ASSISTANT_ROOTS`; uploads check Origin, while downloads rely on the `SameSite=Strict` cookie and reject cross-site `Sec-Fetch-Site`; uploaded file content is not sent to models | The root check only guards against mistakes: the page already has shell privileges, and the user can still read and write any file they have permission for from the terminal |
| Resource exhaustion | Byte-level buffer limits (input, JSON request bodies, single uploaded files, WebSocket messages, SDP, context, TTS text); slow clients are disconnected and fetch a fresh snapshot | No limit on the number of sessions, run time, or number of proposals |

## Out of scope

- Multi-user or multi-tenant access control: there is only one shared password.
- Defending against malicious processes running as the same operating system user.
- Exposing the port directly to the internet. Remote access should use an authorized SSH tunnel, or a self-configured HTTPS reverse proxy with an exact `LIVE_ASSISTANT_ORIGIN`.
